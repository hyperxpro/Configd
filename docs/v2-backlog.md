# v2 backlog

The honest list of what v1 does not do, and the work that would follow. v1 is deliberately scoped: a single-region, sharded-Raft config store with an mTLS edge and a full authentication system, shipped with horizontal scale proven, at-rest encryption available, and leadership auto-balance built. Everything here is designed-or-understood but not built for v1.

> **Shipped since the early backlog (no longer here):** at-rest AES-256-GCM encryption (opt-in), the KMS-provider SPI *and* an external Vault Transit provider, the pluggable authentication SPI *and* the full auth system (No-Auth/Basic/OIDC/mTLS), non-destructive key rotation, leadership auto-balance, chunked InstallSnapshot, multi-shard (N>1) watches, and a conforming Java reference client plus a conformance suite. Those moved from "designed" to "built"; only the genuine residuals below remain.

## Security and encryption

- **Online/admin key rotation trigger.** Term rotation and signing-key rotation are built, crash-atomic, non-destructive, and tested (`NodeKeyring.rotateTerm` / `rewrapForNewSigningKey`, keyring old-term retention), but there is **no online admin trigger** — a rotation is an out-of-band maintenance action on a stopped node. An admin-gated, live rotation flow is the follow-up.
- **Additional off-host KMS providers.** An external Vault Transit provider ships and is discovered via `ServiceLoader` (`configd-kms-vault`). Other custody backends (AWS KMS, GCP KMS, an HSM/PKCS#11 provider) can be added behind the same `KmsProviderFactory` SPI without a core edit; none besides `local` and `vault-transit` ships yet.
- **Audit-log at-rest encryption.** The security-audit HMAC chain is the one at-rest key not term-versioned (it derives from the signing key) and stays **HMAC-only** — audit metadata (config key names, principals) is integrity-protected but not confidential at rest. Encrypting the audit log is a follow-up.
- **N>1 cross-group at-rest integrity (AAD groupId binding).** The GCM AAD binds the artifact-type magic but not the Raft groupId, and one key manager is shared across all groups. Nonce uniqueness is global and safe; cross-group at-rest *integrity* (a record spliced from group B's WAL into group A's) is caught by the Raft log-consistency layer and the per-shard anchor, not the envelope AAD. Binding groupId into the AAD is the tighter belt before an N>1 deployment relies on envelope-level cross-group integrity. (Note: an offset/segment-in-AAD does **not** close *trailing whole-log truncation* — that is closed by the durability **anchor** (`raft-anchor`, dual-slot monotonic), already built.)

## Scale and operations

- **Transfer-on-graceful-shutdown.** Leadership auto-balance ships (a decentralized shed loop, on by default at N>1) and the ADMIN-gated `POST /v1/admin/groups/<id>/transfer-leadership` route is wired. What is not yet built is proactively handing off a group's leadership when a node shuts down: SIGTERM flips readiness to draining (B7) so the orchestrator stops routing, but it does not transfer leadership first — recovery relies on the normal election after the node leaves.
- **Leadership transfer status read.** An ADMIN-gated per-group leadership status read (GET) to confirm the asynchronous `transfer-leadership` took effect and to detect drift; today an operator reads `raft_node_leader_count` / `raft_shard_leader_<gid>`. A GET at `/v1/admin/groups/<id>/leadership` collides on suffix with the existing `POST .../transfer-leadership`, so routing must match the transfer suffix first or use a distinct path. Read-only, off-owner-safe (`leaderId()`/`role()`), reusing the same ADMIN gate.
- **Transfer-abort metric.** The Raft dissertation §3.10 transfer-abort (a stalled leadership transfer auto-aborting after about one election timeout so the current leader resumes) logs to stderr only. A `raft.leadership.transfer.aborted` counter would let monitoring alert on transfer churn. Requires a `ConfigdMetrics` catalog entry plus `EdgeMetricsContractTest` registration (the anti-blind-dashboard gate).
- **N>1 tuning (when multi-shard is enabled).** The owner pool must have at least as many threads as shards, or all shards serialize on one owner thread for no gain; the shard count is capped at 16 (roughly ten or eleven busy leaders saturate a 16-vCPU box). See `docs/archive/measurement/ec2-horizontal-2026-07-01/`.
- **Disk-spilling snapshot reassembly.** Chunked InstallSnapshot ships (a large snapshot streams as ordered chunks, each ≤ 4 MiB; the follower reassembles in heap under a fail-closed `configd.raft.maxReassembledSnapshotBytes` cap). Reassembly is heap-bound; spilling the incoming chunks to disk rather than buffering the whole snapshot in heap is the follow-up.

## Ecosystem

- **Additional-language client drivers.** A conforming **Java** reference client (`configd-client` + `-core`/`-http`/`-edge`) and a `configd-conformance` suite ship and are wired into CI. The driver-protocol RFC (`docs/rfc/driver-protocol/`) is stand-alone implementable end to end, including golden wire vectors, so drivers in other languages (Rust/Go/Python) can be built from it on demand and validated against the same goldens.
- **Disjoint sharded-edge topology.** v1 multi-shard watches are served by a single aggregating endpoint (every node hosts all N groups). A disjoint sharded-edge topology (edges serving shard subsets, the driver merging client-side — the same wire, more connections) is a later increment.
- **Globally-ordered / cross-shard watch.** v1 watches are per-key and per-shard ordered; there is no cross-shard global order (no global clock; cross-shard atomicity is disclaimed). A globally-ordered cross-shard subscription is out of scope by design, not merely deferred.
- **Allocation win.** A measured server-sink allocation reduction (about 176 bytes per operation) is understood and ready to fold in.

## Measurement (a separate later arc)

- **Longer soak, WAN, and literal sustained-throughput measurement.** v1's stability evidence is a **6 h soak (not 24 h / 30 d)**; horizontal scale is proven near-linear (2.45× on 3 machines, single-cluster max 1607 w/s) but **no literal sustained 10 k/s, no 100 k burst, and no cross-region / WAN** run exists. The first-30-days posture is the [burn-in contract](operations/burn-in-contract.md). Closing these is a dedicated measurement arc.
