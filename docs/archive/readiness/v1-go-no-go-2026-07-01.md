> snapshot-4-MiB mitigation (C2 in section 0, and sections 5.2, 5.4, 6). No such alert exists. The

> `ConfigdSnapshotInstallStalled`, fires on `configd_snapshot_install_failed_total`, which is recorded at

> cap-lift, since built) makes the >4 MiB case unreachable. The review's ship recommendation is unaffected

## 0. Recommendation at a glance

**Recommendation: go with conditions.** The system is a well-built, now-empirically-validated region-local
strongly-consistent config control plane. The correctness core is verified; the hard empirical claims
(durability, long-run stability, horizontal scale) are measured green on real hardware; the ADRs the
consistency contract rests on are ratified; encryption-at-rest is a decided later item. No absolute,
deployment-independent blocker survives. What remains is a small, named set of conditions -- mostly
"enforce the documented deployment requirements," plus one cheap pre-ship capture -- not open-ended work.

**The conditions (ship after these; all small/named):**

| # | Condition | Kind | Ref |
|---|---|---|---|
| **C1** | **Ship secure-by-config.** Enable and document auth plus mTLS (and audit plus replay) before any production node; put the §4 must-know list into the operator runsheet as release gates, not footnotes. | Posture + docs (ship-with) | D-3 |
| **C2** | **Publish the deployer must-know requirements** as release gates: don't-store-secrets, legacy-SUBSCRIBE segregation, single-scope-at-N=1, snapshot <4 MiB + drop-alert, leadership-managed horizontal scale. | Docs (ship-with) | §4, §5 |
| **C3** | **Capture a green live multi-process faulted linearizability run on the release commit** (the faulted matrix runs nightly/self-hosted today; the audit's blocker #5). | One cheap pre-ship close | 10.2 |
| **C4** | **Adopt the first-30-days burn-in contract** (heightened alerting, daily error-budget review, predefined rollback triggers, named on-call) and accept the precisely-bounded empirical edges (6 h soak not 24 h; single-box DR topology; no literal 10 k/s; no WAN). | Posture (ship-with) | D-4 |

**Recommended, not required for the ship gate:** merge the EC2-confirmed alloc win (`ByteBufFrameSink`
reuse, ~176 B/op); land a `transferLeadership` admin endpoint / balancer before any deployment relies on
sustained multi-shard horizontal scale.

**The ship line in one sentence.** Durability, availability, and long-run stability are measured and
green; horizontal write scaling is proven near-linear (2.45x on 3 machines, a conservative floor);
single-node throughput is characterized (~800 w/s, churn-bound); the system ships as a single-region,
N=1-default, mTLS-securable strongly-consistent config store with a complete stand-alone protocol RFC,
with encryption built later, client drivers buildable on demand, and leadership-balancing the one
horizontal-scale operability follow-up.

**Two deployment-conditional blockers** (bind only on specific deployment shapes, neither absolute):
encryption-at-rest is a blocker iff the deployment stores secrets or meets a compliance bar (mitigated:
integrity envelope plus documented "don't store secrets" plus edge-in-memory); the snapshot 4 MiB cap is a
blocker iff expected snapshot state exceeds 4 MiB (mitigated: keep state small plus alert on the drop plus
`matchIndex` lag).

### 3.2 The one horizontal-scale operability follow-up (leadership balancing)

Multi-Raft leadership is not auto-balanced at this point -- and the horizontal 2.45x requires exactly one
group-leader per box (1-1-1). At the time that is operator-achieved by fresh-boot-until-balanced (~4-20
boots: a fresh simultaneous boot lands 1-1-1 only ~1 in 20, because whichever node is ready a beat sooner
"sweeps" and wins all its groups) and is a stable fixed point at rest -- but not automatically maintained.
`RaftNode.transferLeadership` (Raft TimeoutNow) exists in core but at this point is not exposed on any
admin HTTP route and not invoked on shutdown, so N groups can pile leaders onto one node and forfeit the
horizontal benefit until a restart. (The aggregate is robust to modest imbalance -- a 2-1-0 placement still
sustained 1,628/s -- but a fully-swept placement is not.) This is a genuine operability gap that gates the
horizontal-scale claim in practice at this point. Follow-up (one item, three options): expose
`transferLeadership` via an admin endpoint, and/or a lightweight balancer, and/or transfer-on-graceful-
shutdown. (Since built -- see `docs/architecture/architecture.md` for the shipped leadership
auto-balancer.) `ec2-horizontal-2026-07-01/05-leadership-placement.md`

### 3.3 Bottom line

The empirical foundation supports: durability, availability, and long-run stability measured green; a
characterized single-node write envelope (~800 w/s, churn-bound, admission-shed-stable); and horizontal
write scaling proven near-linear (2.45x/3-machine, a conservative floor). It does not yet support: an
automatically-maintained horizontal deployment (leadership balancing is manual at this point -- the one
operability gap, since closed); a literal sustained-10k/s or 100k-burst number; a full 24 h/72 h soak; or
any cross-region/WAN claim (out of scope). Ship on the measured envelope with those four edges stated
explicitly.

## 4. The security-posture line

**The honest lead.** The system has a real, code-wired security model -- not an interface-only sketch. It
ships mutual-TLS plus bearer-token authentication, an in-core RBAC authorization foundation
(scope-through-API, the `{READ, LIST, WRITE, WATCH, ADMIN}` capability vocabulary, union-of-ancestors
grants with absolute deny-precedence and default-deny, roles, and policy-as-config under `_acl/`), a
whole-target watch-authorization gate, unconditional rate limiting, at-rest integrity (HMAC-SHA-256),
config signing, and a fail-closed signing-key-co-location guard. The mechanisms are wired into the live
request path (the historical "interface-only" caveat is stale). The design makes one deliberate posture
choice: it is secure-by-config, not secure-by-default. Except for rate limiting, every control is off
until an operator turns it on (each emits a loud startup warning when off). There is one registered gap
that is not a posture choice: config data is not encrypted at rest (integrity is not confidentiality).

**What is built and wired (as of this review):**

| Control | Status | Note |
|---|---|---|
| Authentication -- mTLS (cert-DN) + bearer token | Wired, off by default | Bearer active only with `--auth-token`; constant-time compare (`MessageDigest.isEqual`, `ConfigdServer.java:725`); loud warning when off. A bearer match authenticates as `root` (empty roles) -- so in the default config "authenticated via `--auth-token`" is equivalent to "is root"; control-plane multi-principal separation comes only from `_acl/` policy or the mTLS cert-DN path. mTLS enforced when TLS configured, but TLS is off-by-default, so plaintext out-of-box. A pluggable authN SPI was designed, not yet wired at this point (since built). |
| Authorization -- in-core RBAC (not pluggable) | Wired, active | `AclService` (`Permission{READ,LIST,WRITE,WATCH,ADMIN}`): union of matching ancestor grants, absolute deny-precedence, default-deny; `WATCH` floored by `READ`; role-aware; config-sourced `ConfigPolicy`/`PolicySerializer` under `_acl/`. Default = single `root->ALL`; empty `_acl/` implies byte-identical. |
| Watch-authz (N=1) | Wired, active | `AclServiceWatchAuthorizer`: whole-target `READ` and `WATCH` cover, reject-not-filter, fail-closed on any `Throwable`; `FULL`/`full_chain_verify` restricted to root-only. Bounded revocation under live `_acl/` reload (W7-7). |
| Reserved-prefix ADMIN gate | Wired, active | `_acl/` and `_system/` require `ADMIN` for all methods at the HTTP boundary (mutation plus disclosure); fail-closed; write-time `_acl/` validation returns 400 pre-commit. |
| Rate limiting | Unconditionally on | Global 10k/s plus per-principal; gates before Raft propose. The one control not off-by-default. |
| Signing-key co-location | Fail-closed by default | `enforceSigningKeyNotColocated` throws `SecurityException`; refuses to boot with the key co-located in `dataDir`. HKDF crypto-review flagged pending. |
| At-rest integrity (ADR-0042) | Wired, active | HMAC-SHA-256 keyed / CRC32C, constant-time MAC compare, fail-closed. Tamper-detection, not confidentiality. |
| Encryption at rest | Absent at this point | No `javax.crypto.Cipher`/AES in `src/main` (verified). Config values including `secure/` keys are plaintext `byte[]`. Decided to defer. (Since built -- see the readiness register §8.2.) |

**The deployer must-know list (read this before going live):**
1. **Secure-by-config -- turn the controls on.** The system defaults to plaintext, no auth, no audit, no
   replay protection. Before production you must set `--auth-token`, configure TLS (enforcing mTLS on
   edge/peer), enable the audit log, and enable replay protection. Each is off-by-default with a loud
   warning.
2. **Segregate legacy-SUBSCRIBE from watch clients (the single most important watch condition).** The
   `--edge-port` also serves the pre-existing whole-store SUBSCRIBE fan-out, which has no per-key ACL (the
   trusted server-to-edge backbone, ADR-0038). A cert that completes the mTLS handshake can pull the whole
   store via SUBSCRIBE, bypassing the watch gate. The watch ACL only constrains clients that cannot reach
   SUBSCRIBE -- deploy watch clients segregated from edge-cache subscribers. Not reachable in the default
   config (only `root` can watch, and `root` already holds the whole store), but load-bearing the moment a
   non-root watch is granted on a shared port.
3. **mTLS plus explicit grant for any watch.** A watch needs a verified cert-DN and an explicit `READ` and
   `WATCH` grant; plaintext means all watches are rejected (fail-closed). Out of the box only `root`
   watches.
4. **Encryption is integrity-only -- do not store secrets.** At-rest gives tamper-detection, not
   confidentiality. `secure/` buys read freshness, not secrecy. Keep passwords/tokens/keys/PII in a
   dedicated secret manager. If your deployment must store sensitive data or meet a compliance bar,
   encryption-at-rest was a blocker for you at this point -- raise it before deploying (since resolved,
   encryption is available behind a flag).
5. **`scope` is not an authorization boundary at N=1.** Gate/store/read/filter are uniformly scope-blind;
   `scope` is forward-compat metadata. Do not rely on it for tenant isolation.
6. **Reserved prefixes are ADMIN.** `_acl/` and `_system/` require ADMIN for every method (HTTP boundary;
   no non-root principal can observe reserved keys via any watch kind -- the full-scope grant is root-only).

**Dormant defect, accounted for honestly.** `SigningKeyStore.java:170` (`writeForTest`) computes
`PosixFilePermissions.fromString("rw-------")` but discards it -- the `Files.setPosixFilePermissions` call
is missing, so this helper never chmods 0600. This is a test-only helper with zero production exposure:
production `generateAndWrite` (`:142-144`) correctly applies `OWNER_READ|OWNER_WRITE`. Tracked as a trivial
cleanup; not a blocker.

**Security residuals (tracked follow-up at the time, none a stop-ship on the documented posture):**

auth-SPI wiring (authZ stays in-core by design; since built); hardening -- gate the legacy SUBSCRIBE path /
segregate trust anchors, and move the reserved-prefix rule into `AclService`; residuals from the security
hardening pass (leaf-anchor expiry, active-replay -- the guard is passive-only and opt-in -- WAL

**Verdict (feeds the go/no-go).** The security posture is shippable with the documented deployer

## 6. The ship line and go/no-go recommendation

### 6.1 What is proven

A region-local, strongly-consistent, sharded, mTLS-securable configuration control plane -- a single Raft
root for linearizable writes with asynchronous bounded-staleness fan-out to in-process edge readers:
- **Durable writes** -- fsync-before-ack, no early-ack (ADR-0033); proven 0 committed-write loss under 3
  fault modes on metal.
- **Fast, clean failover** -- proven ~372 ms leader-loss gap, single bounded election; RTO 4.2 s/5.9 s.
- **Horizontally scalable** -- proven near-linear ~2.45x on 3 machines (per-group-independent,
  leadership-managed), cluster-bound by consensus churn not hardware; the scaling path toward the 10 k/s
  aggregate target is evidenced, not just modeled.
- **Long-run stable** -- proven 6 h soak leak/OOM-clean.
- **Sharding server-wired and exercised on metal** -- `StaticShardMap` plus `addGroup` loop plus `shardFor`
  routing plus the 0x02 coalesced-heartbeat frame on main; N>1 measured with the real jar (defaults to
  N=1; N>1+edge fail-closes unless opted in).
- **N=1 client-facing change-subscription** -- RFC §2 watch protocol server-side (whole-target authz,
  bounded revocation).
- **In-core RBAC** -- scope/paths/capabilities/roles/policy-as-config/`_acl/`-ADMIN-enforcement.
- **A complete, stand-alone-implementable protocol RFC** (§0-§7).
- A verified correctness core -- Raft (ReadIndex linearizable reads, pre-vote, joint consensus), 3 TLA+
  specs, Porcupine linearizability, jcstress, mutation-tested (73%), property-fuzzed.

### 6.2 What was deliberately out of scope at this point

The §5.2 list: client drivers, encryption-at-rest build plus KMS SPI, auth-SPI wiring, multi-shard
watches, dynamic resharding, `list` endpoint, segment-aware ACL, BATCH API, cross-region/WAN, sub-second
region failover, the leadership balancer, polyglot bindings, the alloc-win merge. Stated scope, not gaps.
(Many of these have since been built -- see `docs/README.md` and `docs/architecture/architecture.md` for
current status.)

### 6.3 The measured envelope vs. the 10 k/s positioning

- Single-group write knee is approximately 800 w/s (churn-bound). Edge read: p50 50 ns / 53,616 req/s @64
  conn.
- Horizontal aggregate: ~+475-535 w/s per added leader-machine (cross-machine), near-linear, proven to
  1607 w/s @3 machines. The original 10 k/s baseline is a sharded-aggregate target -- now evidenced as a
  real path (~17-19 machines at the cross-machine per-group knee, fewer with bigger instances / group-commit
  tuning), contingent on the leadership-balancing operability work to sustain 1-leader-per-box at scale.

### 6.4 The recommendation: go with conditions

**Reasoning.** The correctness core is verified; the hard empirical claims (durability, stability,
horizontal scale) are now measured green; the sharding server wiring is on main and exercised on metal;
the ADRs the contract rests on are ratified; encryption was a decided later item at this point. No
absolute blocker survives. The conditions (§0: C1-C4) are a small, named set -- three are
"publish/enforce the documented deployment requirements" (the secure-by-config posture is load-bearing
enough that folding it into an unqualified go would understate it), and one (C3) is a single cheap
pre-ship capture. This is not an unqualified go (the secure-by-config posture plus leadership-balancing
gap are real and must ship as named conditions), and it is not a no-go (no absolute, deployment-independent
blocker). The operator ratifies; this review recommends and evidences.
