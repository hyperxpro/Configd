## mTLS posture (important)

The server supports `--tls-cert/--tls-key/--tls-trust-store`, which turns on required mTLS on both the
Raft peer channel and the API (a single `TlsManager`); plaintext otherwise.

- **mTLS is confirmed functional end-to-end on this box**: a 3-node cluster booted with the production
  TLS triple (generated by `deploy/compose/setup-secrets.sh`; server cert SANs cover `127.0.0.1`),
  formed a leader over Raft peer mTLS (`NettyRaftTransport ... (mTLS) [tier=epoll]`), and served the API
  over mTLS -- a `curl --cert server-ks.p12 --cert-type P12 --cacert server.pem GET /health/ready`
  returned 200.
- **The throughput/soak/DR runs themselves are plaintext-loopback**, matching the methodology of the
  `wsC-ladder`/`s75`/soak scripts and keeping the numbers directly comparable to the established ~800/s
  single-group baseline. The Java load driver (`HttpClient`) could not trivially do mTLS -- its default
  `SSLContext` hit `InvalidAlgorithmParameterException: trustAnchors must be non-empty` against the
  empty-password PKCS12 truststore, a JSSE quirk not worth burning the paid session on.
- **Why this is sound**: the scaling shape, the leak/OOM behavior, and the durability/failover semantics
  are all mTLS-invariant -- mTLS adds symmetric-crypto CPU and a handshake on reconnect, but it does not
  change whether throughput scales with N, whether the heap stays flat, or whether a committed write
  survives a kill. The mTLS overhead is a separate, optional arm.
