RR-003 (P0) — restart after compaction = silent data loss
DISCRIMINATING PRE-FIX FAILURE CAPTURE
================================================================================

Finding : RR-003 / CF-42 / triage P0-3. A snapshot is taken in RAM only; the
          compacted WAL prefix is deleted durably; on restart the state machine
          is never restored from the snapshot, so ALL committed state below the
          snapshot point is silently gone. Latent in production only because the
          size/interval trigger is unwired (RR-005, S3) — the loss mechanism is
          complete in committed code. The tests invoke triggerSnapshot() directly.

Pre-fix  : RaftNode.triggerSnapshot (RaftNode.java:370-390) writes the snapshot
defect     ONLY to the RAM field latestSnapshot (:85, write :387); it calls
sites      log.compact(:388) which durably rewrites the WAL (deleting the prefix
           [1..S]) and persists the snapshot BOUNDARY meta — but never the
           snapshot BYTES. There is no persistSnapshot call anywhere, and the
           RaftNode constructor (RaftNode.java:182-216) / ConfigdServer boot
           (ConfigdServer.java:216,270) never call stateMachine.restoreSnapshot
           on recovery. RaftNode.applyCommitted (RaftNode.java:1574-1623) has an
           `if (entry != null)` with NO else: a null (missing/compacted) entry
           is SILENTLY skipped while lastApplied still advances — the loss
           amplifier.

Invariant: at every instant there exists on durable storage a complete prefix
under test  (persisted snapshot at index S + WAL suffix [S+1..lastIndex])
            sufficient to reconstruct ALL committed entries; recovery restores
            snapshot+suffix; a detected gap fails loudly (never silently skips).

Harness  : configd-consensus-core/src/test/java/io/configd/raft/CrashStorage.java
           A crash-capable Storage: every mutating op (put/appendToLog/
           truncateLog/renameLog) is BUFFERED and only promoted to the durable
           image on sync(); crash() discards all un-synced writes. "Restart" =
           build a fresh RaftLog/RaftNode over recoveredView() (the durable
           image only). This unsynced-loss model is what makes fsync removal
           observable (RR-086 foundation). Crash points are armed semantically
           (crashBeforeKeyPut / crashAfterKeyDurable / crashBeforeWalDelete), not
           by raw op counts.
State machine: configd-consensus-core/src/test/java/io/configd/raft/KvStateMachine.java
           A real KV state machine whose snapshot()/restoreSnapshot() faithfully
           round-trip applied state (the InstallSnapshotTest stub does not).
Matrix   : configd-consensus-core/src/test/java/io/configd/raft/SnapshotCrashRecoveryTest.java
           Single-node leader; commit a seed-varied first batch; snapshot+compact
           crashing at point (a) BEFORE persist / (b) AFTER persist BEFORE WAL
           truncate / (c) AFTER truncate (and NONE = clean snapshot, no crash);
           (if not yet crashed) commit a second batch into the WAL suffix; restart
           over the surviving durable image; re-elect (the production recovery
           path) and assert the recovered state machine == the full pre-crash
           committed key/value state. Swept across 60 seeds x 4 crash points plus
           the three named single cells.

Durability model (load-bearing for RR-086): CrashStorage mirrors FileStorage —
           put/appendToLog SELF-fsync (durable on return); truncateLog/renameLog
           are rename-style, durable only after the following sync() (the dir
           fsync). So the snapshot WAL SUFFIX (appended entries) survives a crash,
           but a WAL rewrite whose trailing sync() is deleted (the RR-086 mutant)
           is lost — making fsync removal observable.

LOSS EVIDENCE (the defect, quantified):
  180 / 240 matrix cells lose data; the 60 AFTER_PERSIST_BEFORE_TRUNCATE cells
  pass pre-fix precisely because crashing before the WAL prefix delete leaves the
  full WAL as a safety net. In every losing cell the SNAPSHOTTED PREFIX [1..S] is
  gone from the recovered state machine while the WAL SUFFIX [S+1..] survives
  (e.g. expected={k0,k1,post0} actual={post0}). The purest demonstration is the
  NONE cell: NO crash at all — a clean snapshot followed by a restart — and the
  prefix is already lost, because the snapshot bytes are never persisted (nothing
  is restored on boot) and applyCommitted SILENTLY skips the now-missing [1..S]
  entries (the entry==null branch), advancing lastApplied past them. snapshotIndex
  recovers correctly (e.g. 3) but over a state machine missing everything below it.
  Net: a snapshot+restart = silent loss of all committed state at/below the
  snapshot point.

APPENDIX A — POST-FIX PROOF
================================================================================

Fix commit 5c2ca55 ("S2/RR-003: persist snapshots durably before WAL
truncation; fail loudly on gaps").

The fix, by file:line:
  - RaftLog.persistSnapshot(SnapshotState) (RaftLog.java) — fsync the snapshot
    bytes (Storage.put: temp + force + atomic-rename + dir-fsync) under key
    "raft-log.snapshot" BEFORE compact() deletes the WAL prefix.
  - RaftLog ctor — recover the blob (readSnapshotBlob), accept iff
    blob.lastIncludedIndex == recovered snapshotIndex (else WAL is authoritative).
  - RaftNode.triggerSnapshot — persistSnapshot THEN compact (persist-before-truncate).
  - RaftNode.handleInstallSnapshot — same persist-then-compact (follower path).
  - RaftNode ctor — restore the state machine from the recovered snapshot and
    seed lastApplied = snapshotIndex; if a boundary exists with NO bytes, fire
    durable_prefix_no_gap (loud, never silent).
  - RaftNode.applyCommitted — entry==null on a committed index fires
    durable_prefix_no_gap and stops (no silent lastApplied advance).
