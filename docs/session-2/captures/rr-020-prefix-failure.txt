RR-020 (P1) — GLOBAL/security keys lack the required fail-closed linearizable
strong-read path (ADR-0030 INV-1)
DISCRIMINATING PRE-FIX FAILURE CAPTURE
================================================================================

Finding : RR-020 / CM-097 (carried R-10). ADR-0030 Amendment A1 / INV-1
          (adr-0030...:679-683) mandates: enforcement points MUST fail CLOSED
          (deny) for a GLOBAL/security key when the linearizable root read path
          is unavailable, and MUST NOT fall back to a bounded-stale edge/local
          copy. Pre-fix there was NO strong-read key class, NO enforcement, and
          NO contract entry: a GET with default consistency went straight to the
          node's LOCAL store (HttpApiServer.handleGet -> configStore.get(key)),
          which on a FOLLOWER serves bounded-stale state. A revoked
          security.killswitch could therefore be read as still-permitting on any
          lagging follower — exactly the unbounded-damage case INV-1 forbids.

Pre-fix  : HttpApiServer.handleGet (pre-fix):
defect        boolean linearizable = query != null && query.contains("consistency=linearizable");
              ReadResult result;
              if (linearizable && readService != null) { result = readService.linearizableRead(key); ... }
              else { result = configStore.get(key); }   // <-- secure/ key, default
                                                        //     consistency => LOCAL/STALE
          No branch consulted any notion of a security/GLOBAL key class, so a
          `secure/`-prefixed key was treated like any other config key.

--------------------------------------------------------------------------------
FIX
--------------------------------------------------------------------------------
StrongReadPolicy (new): config-driven key class — a key is strong-read iff it
  starts with one of a configured prefix set (default "secure/"). Blank prefix
  rejected (would match everything). Key-class assignment is config-driven
  pending the fuller ConfigScope story (RR-078, Session 6).
ServerConfig: new --strong-read-prefixes flag (comma-separated); omitted => safe
  default {secure/}; explicit empty => enforcement disabled (deliberate opt-out).
HttpApiServer.handleGet: a strong-read key is ALWAYS served via the linearizable
  ReadIndex path regardless of the requested consistency; if it cannot be served
  (readService null, OR linearizableRead returns null = not leader / ReadIndex
  confirm fails / timeout) -> failClosed(): 503 + "X-Fail-Closed: strong-read" +
  X-Leader-Hint, distinguishing body citing ADR-0030 INV-1, and the local/stale
  value is NEVER written. Ordinary keys are unchanged (stale serving allowed).
ConfigdServer: builds the policy from config.strongReadPrefixes() and passes
  raftNode::leaderId as the X-Leader-Hint source.
