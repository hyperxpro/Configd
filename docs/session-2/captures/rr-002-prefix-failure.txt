================================================================================
RR-002 (P0) — timeout-less blocking connect/TLS handshake on the single Raft
event-loop (tick) thread
DISCRIMINATING PRE-FIX FAILURE CAPTURE
================================================================================

Finding : RR-002 / CF-21 / triage P0-2 (carried R-15). Every RaftNode send
          (tick heartbeat, append-entries replication, vote requests, read
          confirmations) is marshalled onto the SINGLE configd-tick thread
          (ConfigdServer.java:295 tickExecutor; R-01 makes that one thread the
          sole owner of all RaftNode state). That thread reaches the transport
          via RaftNode.transport.send -> RaftTransportAdapter.send ->
          TcpRaftTransport.send -> computeIfAbsent(createPeerConnection) ->
          PeerConnection.sendFrame -> ensureConnected -> createClientSocket.
          createClientSocket performs a BLOCKING, timeout-less connect (and,
          under TLS, a blocking startHandshake). When a peer's address black-
          holes inbound SYNs (DROP, not REJECT), connect() parks the tick thread
          for the full kernel SYN retransmission timeout (~127s on Linux with
          default tcp_syn_retries=6) PER attempt, repeating on the next tick.
          For that whole window the tick thread cannot drive tick(), route
          inbound messages, complete proposes, or service linearizable reads:
          a single black-holed peer freezes the entire node.

Pre-fix  : TcpRaftTransport.createClientSocket (TcpRaftTransport.java):
defect      - plaintext  :343  new Socket(address.getAddress(), address.getPort())
sites                         -- this Socket ctor connects synchronously with NO
                              connect timeout (the only timeout is the OS SYN
                              timeout, ~127s).
            - TLS        :324  factory.createSocket(host, port) connects sync;
                         :340  socket.startHandshake() blocks with no SO_TIMEOUT.
          `grep -rn setSoTimeout configd-transport/src/main` -> 0 hits.
          ensureConnected (:415-432) runs INSIDE PeerConnection.sendLock and is
          reached directly from the caller of send() — i.e. on the tick thread.
          ConnectionManager.canSend (ConnectionManager.java:119) — the backoff
          gate that could have skipped a dead peer — has only test callers
          (dead code); send() never consults it.
          Empirical stall on record: READINESS-LEDGER.md:134; the A3-B linz
          session had to switch its fault injection from iptables DROP to REJECT
          because DROP froze the leader. Reproducing the DROP-freeze and proving
          it is gone is the regression target.

Invariant: the configd-tick thread (and any thread carrying consensus or
under test  request traffic) MUST NEVER block on connect / TLS handshake / DNS.
            A send to a peer with no established connection returns promptly
            (bounded), never parking the caller on socket establishment.
