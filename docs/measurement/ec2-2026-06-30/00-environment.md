## mTLS posture (important)

The server supports `--tls-cert/--tls-key/--tls-trust-store` → **REQUIRED mTLS** on both the Raft peer
channel and the API when set (single `TlsManager`), plaintext otherwise.

- **mTLS was PROVEN functional end-to-end on this box**: a 3-node cluster booted with the production
  TLS triple (generated by `deploy/compose/setup-secrets.sh`; server cert SANs cover `127.0.0.1`),
  formed a leader over Raft peer **mTLS** (`NettyRaftTransport ... (mTLS) [tier=epoll]`), and served
  the API over mTLS — a `curl --cert server-ks.p12 --cert-type P12 --cacert server.pem`
  `GET /health/ready` returned **200**.
- **The throughput/soak/DR runs themselves were PLAINTEXT-loopback**, matching the prior accepted
  methodology (wsC-ladder / s75 / soak all ran plaintext-loopback) and keeping the numbers directly
  comparable to the RR-113 ~800/s baseline the charter references. The Java load driver (`HttpClient`)
  could not trivially do mTLS — its default `SSLContext` hit `InvalidAlgorithmParameterException:
  trustAnchors must be non-empty` against the empty-password PKCS12 truststore, a JSSE quirk not worth
  burning the paid session on.
- **Why this is sound**: the scaling *shape*, the leak/OOM behaviour, and the durability/failover
  semantics are all **mTLS-invariant** — mTLS adds symmetric-crypto CPU + a handshake on reconnect, it
  does not change whether throughput scales with N, whether the heap stays flat, or whether a committed
  write survives a kill. The mTLS overhead is a separate (optional) arm.
